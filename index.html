🗄️ Section 1

Data Foundation & Synthetic Data

Before any algorithm runs, the workspace needs a governed, layered data estate and realistic data that can be used without exposing production PII. Both problems are solved up front.

Medallion Architecture — Bronze → Silver → Gold

Bronze
Raw Ingest
Synthetic CSV files uploaded to a Databricks Volume under the governed Unity Catalog path. Ingestion notebooks land records as-is; no transformations applied.
Silver
Cleansed & Dedup-Ready
Standardised customer records, duplicate candidate tables, deactivation and reactivation staging tables. The deduplication logic operates at this layer.
Gold
Operational & Reporting
Resolved, trustworthy customer master. Consumed by downstream analytics and validated by the AI Test Factory against expected outcomes.
📦

Synthetic / SONIC-Style Data Sets

Engineered CSV data sets are generated to mirror production record structures — customer IDs, name variants, address permutations, and edge-case duplicates — without containing real PII.

  • Pushed directly to a Databricks Volume under the governed catalog path (e.g. huron_singapore_dma_…)
  • Ingested by SONIC_ingest_all_tables.py-style pipeline scripts into bronze tables
  • Covers deduplication categories: Whole-block, Cross-block, Exact, Fuzzy, Alias/DBA, Master/Sub, Test-block, False Positive/Negative, Operational
✅

Why Synthetic Data Matters Here

The Customer360 deduplication pipeline is sensitive to record variety. Synthetic data delivers three specific benefits:

  • Repeatable demos — same inputs, predictable outputs every run; no dependency on a production data extract
  • Safe testing — engineers test fuzzy-match thresholds and blocking rules against known ground-truth labels, not guessed outcomes from real records
  • Alignment with dedup patterns — each synthetic record class maps to a scenario category in the AI Test Factory, closing the loop from data creation to test validation
💡
Unity Catalog path convention
All prototype work is scoped to a single governed catalog (e.g. huron_singapore_dma_7405609331421419). This single-catalog constraint is enforced in Cursor rules so AI-driven operations cannot accidentally write to a production or shared catalog.
✏️ Section 2

AI-Assisted Design

Architecture thinking and platform decisions are captured in Git as living documents — not slide decks. The Cursor + Databricks MCP stack then connects those decisions directly to a live workspace, so the design and the implementation stay in sync.

🗂️

Repository Layout & Git-First Architecture

A two-tier repo structure separates shared infrastructure from per-engineer work areas. Main path holds docs, shared scripts, and config templates. Per-user folders (e.g. ppandya/) isolate experimental notebooks until they are ready to promote.

  • Config examples live in Git; secrets stay local
  • Databricks Git folder syncs from the same repo — one source of truth
  • Per-member folder model prevents cross-team notebook conflicts
🔌

Cursor + Databricks MCP

The databricks-mcp-server (via npx) is wired into Cursor through .cursor/mcp.json. This gives the AI IDE live awareness of the workspace during design — it can enumerate catalogs, schemas, tables, warehouses, and running clusters without context-switching to the Databricks UI.

  • Catalog/schema discovery at design time, not guesswork
  • Optional Jira MCP for work-item creation inline
  • Additional MCPs (AWS, others) configurable per project rules
👥

Team Artifacts & Role-Based Prompts

Project structure docs, MCP setup guides, and onboarding runbooks are committed alongside code. Role-specific prompt libraries exist for both data developers and QA engineers, framing the full SDLC arc:

  • HLD → implementation prompt sequence
  • Code review prompt (safety rules enforced)
  • Test scenario generation prompt
  • Handover checklist prompt

⚙️ Section 3

AI-Assisted Build

Implementation happens in notebooks and Python/SQL scripts that are structured exactly as the architecture dictates. The Databricks SDK and REST API handle connectivity, leaving engineers to focus on business logic rather than plumbing.

Connectivity & Credential Resolution

The connection verification script (scripts/verify_databricks_connection.py) resolves credentials in priority order: environment variables → .databricks/config CLI profile → explicit PAT. It then calls the SCIM API, lists clusters, and confirms workspace access — all before any notebook runs.

Priority order (from script):
1. DATABRICKS_HOST + DATABRICKS_TOKEN env vars
2. ~/.databricks/config  [DEFAULT] profile
3. Explicit PAT fallback
→ SCIM call to confirm auth
→ Cluster list via REST 2.0

Notebook & Job Execution

The run script (scripts/run_databricks_test.py) creates or imports a notebook, submits a job run via the Jobs API 2.1, polls run state every 30 seconds, and surfaces the run URL on completion — the same pattern the AI Test Factory uses for validation scripts.

SDK vs Raw Requests — When Each is Used

📦

Databricks SDK (databricks-sdk)

Used for high-level Unity Catalog operations: WorkspaceClient().catalogs.list(), schema enumeration, warehouse queries. Handles auth token refresh automatically.

🌐

Raw requests (REST 2.0 / 2.1)

Used for job submission, run polling, and SCIM calls where the SDK adds unnecessary abstraction. Direct API calls make state transitions explicit and easy to log.

⚡

MCP Tooling (Design-Time)

Databricks MCP tools are used inside Cursor during development — not in production notebooks. They provide catalog/schema context to the AI so generated code references real table paths.

AI-Assisted Code Review

AI-assisted review does not mean review-free shipping. Cursor rules and Jira scoping ensure that AI-generated code and work items are governable, bounded, and human-confirmed before anything consequential happens.

Cursor Rules Layer (.cursor/rules/*.mdc)

1

Catalog Scope Enforcement

Rules restrict AI operations to the single designated Unity Catalog. Any generated code that references a different catalog is flagged before execution.

UC scopepre-execution
2

Dangerous Operations Policy

Bulk DELETE or DROP operations affecting more than 100 rows require triple acknowledgment: the engineer must confirm the intent, the target table, and the row count before the statement is permitted. Read-only PAT is the preferred connection for exploratory work.

Tool Routing Rules

Rules specify when to use Databricks MCP (catalog/schema queries), when to use Jira MCP (defect creation), and when to use native IDE capabilities — preventing AI from calling the wrong tool for a given context.

The 6-Step Factory Loop

1

Environment Discovery

The AI agent uses Databricks MCP to enumerate the live workspace: catalogs, schemas, tables (duplicate log, deactivation, reactivation staging), warehouses, and cluster state. No hardcoded paths — the factory adapts to the current workspace layout.

Databricks MCPcatalog discovery
2

Rule Extraction from Docs & Notebooks

The context file and rule catalog are loaded. The agent reads deduplication business rules from documentation and existing notebook logic, then maps each rule to a test scenario category (WB, CB, EX, FZ, AD, MS, TB, FP, FN, OP).

context filerule catalog
3

Scenario & Workbook Alignment

Markdown test scenarios are aligned with the Excel workbook package: test cases seeded into 02_Test_Cases, scenario coverage confirmed against 01_Test_Scenarios, DQ rules checked in 06_DQ_Rule_Register. Python sync scripts populate workbooks from repo content.

77 scenariosExcel package
4

Validation Script Execution

Four PySpark/SQL scripts run against the live silver tables via the job runner (REST API 2.1 or batch). Each script targets a specific validation domain:

  • duplicate_log_rules — duplicate candidate rule correctness
  • threshold_boundaries — fuzzy-match score boundary behaviour
  • false_positive_negative — FP/FN detection against labelled ground truth
  • operational_pipeline — end-to-end pipeline run integrity
4 scriptsREST 2.1
5

Structured Execution Results & Post-Run Sync

Results are written to a markdown execution tracker and to 03_Execution_Results and 04_Traceability workbooks via sync_test_factory_post_run.py. Each test record shows: scenario ID, PASS/FAIL, actual vs expected, and defect ID if raised.

post-run synctraceability
6

Automatic Jira Defect Creation

On any FAIL result the agent calls the Jira MCP to create a Bug in project DP under epic DP-4. Labels are derived from the test category; the generated Jira key is written back to the execution tracker — closing the loop from test failure to backlog item without manual copy-paste.

FAIL → JiraDP / DP-4auto writeback

Human-in-the-Loop Requirements

🔍

FP/FN Review

False positive and false negative results require human review before a defect is raised. The AI flags them; a data engineer confirms whether the deduplication logic or the test expectation needs updating.

⛔

Production Changes

No test factory result triggers a production change automatically. All silver-table modifications from a failed test cycle require explicit human sign-off, separate from the defect creation flow.

🎯

Threshold Tuning

Fuzzy-match score thresholds surfaced by threshold_boundaries script are reviewed by a domain expert. The AI factory identifies the boundary behaviour; the expert decides if the threshold warrants a change.

📋

Jira Defect Triage

Auto-created Jira bugs are assigned to the configured default assignee but require human triage before moving to In Progress. Severity and priority are set by the engineer, not the AI.

✅

Scenario Sign-Off

New test scenarios added by the AI agent are reviewed against the ground-truth label set before being committed to the scenario library. Prevents compound errors in future regression runs.

🗂️

DQ Rule Changes

Updates to the 06_DQ_Rule_Register that affect threshold or owner fields require an explicit PR review. The AI can draft the change; a data steward approves it.

Four Reuse Pillars

⚡

Velocity

From blank Unity Catalog to running tests in a fraction of the time. MCP-driven catalog awareness eliminates table-path guesswork; the job runner handles submission and polling automatically.

🏛️

Quality & Governance

UC-aligned paths, single-catalog scope, explicit safety rules, and auto-traced defects. Quality is structural, not dependent on any individual's diligence.

♻️

Reusability

Clone one repo, merge the MCP config, run the same prompts and scripts. A new team member can execute the full factory without tribal knowledge. No parallel shadow tooling.

🤝

Honest Boundaries

Production changes, destructive SQL, threshold tuning, and defect triage remain human decisions. The factory accelerates the work that can be automated; it does not bypass the judgement that cannot.
